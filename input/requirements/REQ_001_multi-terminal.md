## 1. 一言でいうと

**「プロジェクトのフォルダツリー」と「そのプロジェクトのターミナル」だけを、1ウィンドウで複数プロジェクト分持てる macOS ネイティブアプリ。** エディタは持たない。

## 2. 背景と課題

- [確定] 現状は VSCode をプロジェクトごとに複数起動し、その統合ターミナルで Claude Code / Codex を動かしている。
- [確定] VSCode のエディタ機能はほぼ使っておらず、メモリだけ食っている。
- [確定] ただし VSCode の「ファイル構成が見える」「ファイルパスを取得できる」は手放したくない。
- [確定] cmux は方向性は近いが機能が多すぎる。tmux はツリーがない。
- 結論：**VSCode から「エクスプローラ＋ターミナル」だけを抜き出し、マルチプロジェクト化したもの**が欲しい。

## 3. ゴール / 非ゴール

### ゴール
- G1. 1ウィンドウで複数プロジェクトを切り替えて作業できる。
- G2. 左ペインのツリーと右ペインのターミナルが、常に同じプロジェクトを指す（タイル表示ではフォーカス中のタイルのプロジェクト）。どれとどれが対応しているかは、プロジェクト色で一目で分かる。
- G3. ツリーからファイルパスを最短手数でターミナル（＝AIエージェントへの入力）に渡せる。
- G4. VSCode 複数起動より明確に軽い（§7 の数値目標）。
- G5. Apple 公証済みの .app として自分の Mac に入れられる。

### 非ゴール（やらないことを固定する）
- N1. テキストエディタ、差分ビューア、LSP、拡張機能機構
- N2. 内蔵ブラウザ、AIエージェントのオーケストレーション、CLI/ソケットによる外部制御
- N3. アプリ終了をまたいだプロセス維持（tmux の detach/attach 相当）
- N4. SSH/リモート接続、Windows/Linux 対応
- N5. Mac App Store 配布、自動アップデート、多言語化、他人向けの設定UIの作り込み
- N6. 自由分割（任意の位置・比率でペインを割る tmux 風レイアウト）。複数同時表示は自動グリッドのタイル表示のみ
- N7. ファイルの中身に触れる機能（内容のプレビューペイン、編集、全文検索、差分）。ツリーが扱うのはファイルの「置き場所と名前」まで。git worktree の作成・削除などの git 操作も持たない

> 判断基準：迷ったら「VSCode を閉じられるか」に効くものだけ入れる。効かないものは N に追加する。

## 4. 利用者と利用シーン

利用者は本人のみ。代表シーン：

1. **朝の立ち上げ**：アプリを開くと前回の 4〜6 プロジェクトが並んでいる。プロジェクトを選ぶとターミナルがそのルートで開いており、`claude` を打つだけ。
2. **並行作業**：プロジェクトAで Claude Code が作業中、Bに切り替えて Codex に指示。Aのエージェントが入力待ちになったら、左のプロジェクト一覧で気づける。
3. **ファイルを指示に含める**：ツリーでファイルを見つけ、ドラッグ（またはショートカット）で相対パスをターミナルの入力行に挿入。
4. **構成の確認**：エージェントが作ったファイルがツリーに即時反映され、何が増えたか分かる。

### 4.1 プロジェクトの定義 [確定]

**プロジェクト＝ユーザーが登録した 1 つのルートフォルダ。** カード 1 枚＝プロジェクト 1 つ＝ルートフォルダ 1 つ。

- 持つもの：ルートフォルダ、表示名（既定はフォルダ名）、プロジェクト色、1 つ以上のターミナル、ツリーの表示状態
- git リポジトリである必要はない。プロジェクトのフォルダ内に Arin の設定ファイルは一切書き込まない
- 1 プロジェクトに複数ルートは持てない
- **同じフォルダの二重登録は弾く**
- **入れ子は許す**（`~/dev/app` と `~/dev/app/frontend` を別プロジェクトにできる）
- **git worktree は特別扱いしない。** worktree のフォルダも通常のプロジェクトとして登録する。見分けやすいようカードにブランチ名を出す（FR-P12）
- **ターミナルの所属は「どのプロジェクトで開いたか」で決まる。** `cd` でルートの外へ出ても所属は変わらない
- **フォルダの移動・改名には自動で追従する**（FR-P07）

#### 6.2.2 AI エージェントとの同時操作 [確定]

ツリーを操作している間も、ターミナルでは AI エージェントが同じフォルダのファイルを書き換えている。方針は **「止めない・見せる・戻せる」**。

- **止めない**：エージェントの実行中もファイル操作をロックしない（エージェントはほぼ常に動いているため、ロックすると使えなくなる）
- **見せる**：エージェントが今どこを触っているかを表示し、人間が衝突を避けられるようにする
- **戻せる**：誤操作しても失わない（ゴミ箱、上書き確認、取り消し。FR-T16／T18／T20）
- 位置づけ：ツリーの操作は「人間がやる軽い片付け」用。構成を大きく変える整理はエージェントに依頼する（エージェント自身が変更を把握でき、古いパスへの書き戻しによる二重化が起きない）

| ID | 優先 | 要求 |
|---|---|---|
| FR-T24 | P0 | 判定と実行を一体にする。対象の存在確認と名前衝突の判定は、メニューを開いた時点ではなく**実行の瞬間**に行う。対象が既に無い場合は何も変更せず、理由を表示してツリーを再読込する |
| FR-T25 | P0 | 操作中はツリーの並びを固定する。ドラッグ中・インライン名前入力中・コンテキストメニュー表示中は、ファイル監視による更新を保留し、操作の終了後にまとめて反映する（行がずれて狙いと違う対象を操作する事故を防ぐ） |
| FR-T26 | P1 | 最近変更されたファイルに目印を付ける。ファイル監視で検知した追加・変更を対象とし、目印は時間とともに薄れて消える（既定 30 秒 [仮定]）。折りたたまれたフォルダの中で変更があれば、そのフォルダに目印を出す |
| FR-P13 | P1 | カードに「実行中」の印を出す。そのプロジェクトのいずれかのターミナルで、シェル以外のプロセスが前面で動いている間だけ表示する |

- AC-T24：Given メニューを開いた後に対象ファイルが外部から削除された / When 「名称変更」を確定 / Then ファイルシステムは変更されず、「見つかりません」と表示され、ツリーから当該行が消える。
- AC-T25：Given `src/a.ts` をドラッグ中 / When 外部から `src` に 100 ファイルが追加される / Then ドロップするまでツリーの行は動かず、ドロップ後に 100 ファイルが反映される。
- AC-T26：Given `src` が展開済み / When 外部から `src/b.ts` が変更される / Then `b.ts` に目印が付き、30 秒後に消える。
- **やらないこと**：実行中のロック。エージェントがどのファイルを開いているかの把握（エージェント側との連携が必要で N2 に当たる）。
- **見送り（ドッグフーディング後に再検討）**：直近に変更されたファイルを移動・改名・削除する際の追加警告。

## 8. 制約・技術方針（`/architecture` への入力）

`/prd` 段階では技術を確定しない。以下は制約と推奨案であり、最終判断は設計ゲートで ADR に残す。

- **C1 [確定] macOS 専用・公証必須。** Developer ID 署名＋Hardened Runtime＋`notarytool`＋staple。配布は自分用の .dmg / .zip。
- **C2 App Sandbox は無効。** シェルを自由に動かすために必須。App Store 非対応は N5 と整合。
- **C3 [推奨] Swift 6 / SwiftUI + AppKit のネイティブ実装。** Electron/Tauri は G4（軽さ）と矛盾するため不採用。
- **C4 ターミナルエンジンは差し替え可能にする。** `TerminalEngine` プロトコルの裏に隠し、UI から直接依存しない。

| 候補 | 長所 | 短所 |
|---|---|---|
| **SwiftTerm**（v1 推奨） | 純 Swift・SPM 一発・MIT。`swift build` / `swift test` だけで回るので AI 自律開発と CI が単純。PTY 接続ビュー同梱 | 描画性能と細部の互換性は libghostty に劣る可能性 |
| libghostty（GhosttyKit） | cmux と同じエンジン。GPU 描画で高速・互換性が高い | Zig ビルドまたはプリビルド xcframework への依存。埋め込み API の安定性は要確認。ビルドと公証の手順が重くなる |

  - 進め方：M1 で SwiftTerm により FR-M03 の検証（Claude Code / Codex 実機）を最優先で行い、不合格なら libghostty へ切替える。これが本プロジェクト最大の技術リスク。
- **C5 構成方針**：ロジック（プロジェクト管理・ツリーモデル・パス整形・永続化・通知判定）は GUI 非依存の SPM ターゲットに置き、ユニットテストで網羅。アプリターゲットは薄く保つ。
- **C6 依存は最小限。** 追加ライブラリは ADR で理由を残す。
- **C7 ファイル監視は FSEvents。** 除外ディレクトリは監視対象外にしてコストを抑える。

## 9. AI 自律開発のための前提（ハーネスへの要求）

強い自律で回すために、**AI が自分で合否を判定できる状態**を先に作る。

1. **ワンコマンド検証**：`make build` / `make test` / `make lint` / `make app`（.app 生成）を M0 で用意し、`project-config.md` §3 に登録する。
2. **テスト方針**
   - 単体：パス整形・シェルエスケープ、除外判定、ツリー差分適用、状態の保存／復元／破損回復、アテンション判定（BEL/OSC パース）、タイルのグリッド／ページ割り当て、プロジェクト色の割当
   - ファイル操作：一時ディレクトリ上で新規作成・名称変更・移動・コピー・ゴミ箱・名前衝突・取り消しを自動テスト。**テストは必ず一時ディレクトリ内で行い、実プロジェクトのファイルに触れない**
   - 同時操作：操作の途中で外部からファイルを削除・追加する状況を再現し、FR-T24（実行時判定）と FR-T25（更新の保留）を自動テスト
   - 結合：実 PTY でシェルを起動し、cwd・環境変数・出力継続（AC-M02/M04）を検証。FSEvents は一時ディレクトリで検証（AC-T02）
   - UI：XCUITest はスモークのみ（起動→プロジェクト追加→切替）。見た目は人間が確認
3. **人間ゲート（AI に任せないこと）**
   - 署名・公証の秘密情報（証明書、App Store Connect API キー）の取り扱い。AI は手順書とスクリプトまで。実行は人間、または GitHub Secrets 経由の CI のみ
   - 実機での体感確認（IME、TUI 表示、ドラッグ操作）— 各マイルストーン末に 1 回
   - §3 非ゴールの変更
4. **スコープ逸脱の禁止**：非ゴール N1〜N7 に触れる実装を見つけたら、実装せず提案として記録する。
5. **CI**：GitHub Actions の macOS ランナーで build / test / lint。公証は tag push 時のみ。
6. **進め方**：縦切りで 1 マイルストーン＝動く .app。各マイルストーン完了時に AC の合否一覧を `testreport/` に出力する。

## 12. リスク

| リスク | 対応 |
|---|---|
| ターミナルエンジンの互換性不足（TUI 崩れ、IME） | M1 を検証専用にし Go/No-Go。エンジン抽象化で差し替え可能に |

| タイル 9 枚の同時描画が重い（G4 の軽さと衝突） | 表示中ページだけ描画。NFR-09 を性能テスト化し、M4 で人間が体感判定。エンジン選定（ADR-001）の評価項目に加える |
