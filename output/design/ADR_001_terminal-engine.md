# ADR-001: ターミナルエンジンに xterm.js 6.0.0 を使い、描画は DOM を既定にする(M1 の Go/No-Go の結果)

- ステータス: Accepted
- 日付: 2026-11-15
- 決定者: 本人(M1 の Go/No-Go。T26)。本人が明示しなかった項目は、本人が試した構成(既定のまま)を採り、下の「決めていないこと」に分けて書いた
- 関連: `ARCH_multi-terminal.md` §2.2、§4、§5.1、§12、§14、§15.2 #9。ADR-003(画面のフレームワーク)、ADR-004(PTY と出力の流し方)。`output/tasks/M1_GO-NO-GO_CHECKLIST.md`

## コンテキスト

Arin は Tauri(WKWebView)の上でターミナルを描く。PRD §7 は、ターミナル 1 枚の段階(M1)で Claude Code と Codex が実用に耐えるかを本人が判定し、耐えなければ描画方式の変更か実装技術の見直し(Swift ネイティブへ戻すことを含む)を行うと定めている。

M1 で作ったもの(T14〜T25): ログインシェルを PTY で起動し、出力を流量制御つきで xterm.js に流し、入力・寸法・コピー/ペーストをつなぐターミナル 1 枚。比べるために、描画方式(DOM / WebGL)と全角幅の方式(`unicode11` / `graphemes`)を起動時の環境変数で切り替えられるようにした。

本人がいちばん重く見た判定基準は、「日本語入力と Claude Code の体感が、普段のターミナルと比べて我慢できる範囲か」である。複数枚の同時表示は、枚数の上限を減らすことで調整できるものとして、判定の決め手にしなかった(本人の発言、2026-11-15)。

## Go/No-Go の結果

**Go。** M2(マルチプロジェクト)に進む。

- 本人が確かめたこと(2026-11-15): 配布版の `.app` を既定の構成(DOM 描画、`unicode11`)で起動し、Claude Code を起動した。本人の発言は「普通に起動して、Claude起動してみたよ。良さそうだ。」「そのまま進めて。」
- 手順書(`M1_GO-NO-GO_CHECKLIST.md`)の 12 項目を 1 つずつ記入した結果は無い。項目ごとの状態は下の「確かめた範囲」に書いた。

### 起動時の指定の扱い

`ARIN_RENDERER`・`ARIN_UNICODE`・`ARIN_VERIFY_GRID` と、いまの描画方式の表示(`RendererLabel`)は、検証用としてリリースビルドでも有効なまま **M4(T49)まで残す**。計画(T27)は、決まらなかった方を M1 の締めで外すとしていたが、上の理由で先に延ばした。配布(M5 の署名・公証)までには、外すか、設定の項目に移すかのどちらかにする。

## M4 の実測と案(計画書 T49b。2026-11-15)

> **ここに書くのは案で、決定ではない。** 描画方式と全角幅の方式は、本人が T50a で 9 枚の体感を比べてから決め、T50b でこの ADR の「判断」の表を直す。

計測は `npm run perf` の 1 回(`testreport/perf/perf-20261115-230233.md`。Apple M5、macOS 26、release ビルド。`.app` は 22:41 のビルドで、タイル表示まで入ったもの)。どれも記録だけで、合否にしない。計測のあいだのシステムのメモリの空きは 74〜76%。

### 実測(Rust 側。PTY → `SessionRegistry` → 偽の送り先。各 3 回の中央値)

| 項目 | 1 枚 | 9 枚同時 | 1 枚(ベル入り) | 9 枚同時(ベル入り) |
| ---- | ---: | ---: | ---: | ---: |
| `yes \| head -c 4 MiB` を流し終えるまで(最初の開始→最後の終わり) | 39.5 ms | 364.0 ms | 37.2 ms | 349.6 ms |
| 全体のスループット | 102.5 MiB/s | 100.1 MiB/s | 107.7 MiB/s | 104.2 MiB/s |
| 未処理の量の最大値(処理済みをすぐ返す送り先) | 66,912 B | 67,814 B | 67,479 B | 67,063 B |

- 9 枚は 1 枚の約 9 倍の時間で、全体のスループットは 1 枚とほぼ同じ(シェルと PTY の側が律速。セッションの数で遅くならない)
- **アテンションの走査(T48c で常に走査するようにした)で遅くなっていない**: 10 万行の `cat`(2a)は 38.7 ms・190.8 MiB/s で、走査を入れる前の記録(`perf-20261115-205753`: 39.8 ms・185.2 MiB/s)と同じ範囲。行ごとにベルを入れて、読み取りの塊ごとに Workspace のロックを取らせても、上の表のとおり差は出ない。走査器だけの速さはメモリ上で約 557 MiB/s(7.7 MB を 13 ms。2e)
- **流量制御は 9 枚でも 1 枚と同じ値で頭打ちになる**: 処理済みを返さない送り先で各 8 MiB を流すと、9 枚とも 524,298〜524,790 B で読み取りが止まり(合計 約 4.5 MiB)、止めたまま最後まで届いたものは 0 枚。テストのプロセスの RSS は増えない。処理済みを返すと 9 枚が 626 ms で最後まで届く(2d)

### 実測(実アプリ。9 プロジェクト・各 1 タブ、`ui.displayMode: "tiles"`。各 2 回の中央値)

| 項目 | DOM | WebGL | DOM・流す | WebGL・流す |
| ---- | ---: | ---: | ---: | ---: |
| 起動→シェルが 9 個揃う(画面が 9 枚とも接続) | 317 ms | 429 ms | 320 ms | 324 ms |
| 本体(footprint) | 26.1 MiB | 26.3 MiB | 31.5 MiB | 30.8 MiB |
| WebKit の補助プロセスの合計(footprint) | 75.5 MiB | 95.4 MiB | 171.5 MiB | 189.4 MiB |
| 本体 + WebKit(footprint) | 101.6 MiB | 121.7 MiB | 203.0 MiB | 220.3 MiB |
| 起動→9 枚が 4 MiB ずつ流し終える | — | — | 1,002 ms | 1,005 ms |
| 1 枚が流し終えるまで(9 枚の中央値) | — | — | 534 ms | 553 ms |
| 流しているあいだの WebKit の RSS の最大 | — | — | 499.8 MiB | 494.0 MiB |
| 画面の失敗の行(WebGL を作れず DOM に戻した報告など) | 0 | 0 | 0 | 0 |

- 比較: 5 プロジェクト・タブ表示(NFR-001 の条件)は本体 25.7 MiB、本体 + WebKit 90.8 MiB
- 「流す」は各シェルが起動直後に `yes | head -c 4194304` を流す組(一時フォルダの HOME の `.zshrc`)。実機の WKWebView が取り込んで処理済みを返す速さで決まり、9 枚の合計で約 50〜70 MiB/s。DOM と WebGL で差は無い
- 流し終えたあとの WebKit の footprint が 75 → 172 MiB に増えるのは、9 枚のスクロールバック(各 10,000 行)が埋まった分と見ている【仮定】。流す量を変えて頭打ちになるか(長く流しても増え続けないか)は測っていない(下の「本人が見ること」)
- WebGL の 9 枚で、コンテキストが足りずに DOM へ戻ることは無かった(画面の失敗の行が 0)

### 実測(画面側。Playwright の WebKit 27.2、偽の Rust 側。10 プロジェクトのタイル表示の 1 ページ目の 9 枚に 2 MiB ずつ同時に流す。各 2 回の中央値)

| 項目 | DOM・unicode11 | WebGL・unicode11 | DOM・graphemes | WebGL・graphemes |
| ---- | ---: | ---: | ---: | ---: |
| 9 枚が取り込み終えるまで | 375 ms | 338 ms | 402 ms | 360 ms |
| 取り込みの速さ(9 枚の合計) | 48.1 MiB/s | 53.7 MiB/s | 44.8 MiB/s | 50.0 MiB/s |
| フレームの間隔の 95 パーセンタイル | 45.0 ms | 36.5 ms | 51.5 ms | 49.0 ms |
| フレームの間隔の最大 | 126.5 ms | 120.0 ms | 129.5 ms | 117.0 ms |
| 50 ms を超えたフレームの割合 | 16.7 % | 20.0 % | 43.1 % | 17.2 % |
| 2 ページ目の写し→描き終わり(9 枚を隠す) | 38.5 ms | 80.0 ms | 36.0 ms | 85.0 ms |
| 1 ページ目の写し→描き終わり(9 枚を出し直す) | 65.0 ms | 63.5 ms | 66.0 ms | 62.0 ms |
| WebGL の canvas の数 | 0 | 18 | 0 | 18 |
| 画面の失敗の報告 | 0 | 0 | 0 | 0 |

- 流量制御は偽物の側で製品の値(未処理 512 KiB まで、64 KiB ずつ、4 ms ごと)を真似た。WKWebView の実機とは別のビルドなので、組どうしの比較にだけ使う
- 流しているあいだのタイルのクリック・キー入力・次のページのボタンから画面がコマンドを呼ぶまでは、どの組も 0〜8 ms。ただし入力のイベントが届くまでの待ち(主スレッドが塞がっている時間)は含まないので、体感の代わりにはならない
- WebGL は 1 枚に canvas が 2 つ(addon-webgl 0.19.0)で、9 枚で 18。隠すとコンテキストを返すので、ページを送るときの描き替えが DOM より約 40 ms 遅い

### 案(本人が T50a で選ぶ)

| 項目 | 案 | 理由 |
| ---- | -- | ---- |
| 描画方式 | **DOM を既定のままにする** | 実アプリでは 9 枚に流したときの取り込み(1,002 ms と 1,005 ms)も起動も差が無く、WebGL は WebKit のメモリが 9 枚で約 20 MiB 多い(GPU のプロセスと canvas の分)。画面側の計測では WebGL の取り込みが約 1 割速く、フレームの間隔の 95 パーセンタイルも少し短いが、ページ送りの描き替えは DOM の約半分の時間で済む。差が小さいので、本人が M1 で試して良いとした DOM を変える根拠にならない |
| 全角幅の方式 | **`unicode11` を既定のままにする** | `graphemes` は取り込みが 5〜7 % 遅く、DOM では 50 ms を超えるフレームが多い(43 % と 17 %)。絵文字の修飾子などの幅の正しさは `graphemes` が上だが、Claude Code の表示で崩れるという報告は本人から出ていない |
| 選ばなかった方式 | **T50b で `ARIN_RENDERER`・`ARIN_UNICODE`・`get_launch_options`・`RendererLabel` を外し、`@xterm/addon-webgl` と `@xterm/addon-unicode-graphemes` も依存から外す** | 配布(M5)までに外すと決めている(上の「起動時の指定の扱い」)。設定の項目(M4.5)に移すのは、本人が T50a で WebGL か `graphemes` のほうが良いと感じたときだけにする(残すとテストと切替の仕組みを持ち続けることになる)。外すかどうかは本人の判断が要る点(計画書 T50b) |
| 流量制御のしきい値 | **変えない**(上限 512 KiB、下限 128 KiB、まとめ 4 ms か 64 KiB、読み取り 16 KiB) | 9 枚でも各セッションが 1 枚と同じ値で頭打ちになり、画面が一度に抱えうる量は 9 枚で約 4.5 MiB に収まる。9 枚同時のスループットは 1 枚と同じで、セッションごとのしきい値を下げる理由が無い |

### 本人が見ること(T50a。自動の計測では分からない)

- 9 枚で Claude Code などを動かし、いくつかで `yes` を流しながら、ページ送り・タイルのクリック・入力が我慢できる速さか(NFR-009)。既定(DOM、`unicode11`)と `ARIN_RENDERER=webgl`・`ARIN_UNICODE=graphemes` で同じことをして比べる
- 長く流しっぱなしにしたとき、アクティビティモニタで WebKit(WebContent)のメモリが増え続けないか(計測は 1 枚 4 MiB までしか流していない)
- WebGL の 9 枚の見た目(にじみ・罫線)と、ページを送ったときのちらつき

## 検討した代替案

- **WebGL を既定にする**: 複数枚では速い見込みだが、本人が試していない。WebView には WebGL のコンテキスト数の上限があり、9 枚を超えたときの挙動も未確認。M4 で実測して決める。
- **比べずに WebGL と `graphemes` を外す**(計画どおり): コードは減るが、M4 で必要になったときに入れ直すことになる。切り替えの仕組みは小さく、テストもあるので、残す負担のほうが小さい。
- **Electron**: 同じ xterm.js が Chromium で動くので WKWebView 固有の心配は減るが、サイズとメモリが増え、「ライト」という狙いから外れる。Go になったので採らない。
- **Swift ネイティブ**: 日本語入力と体感は最良の見込みだが、ツリーやタブの UI を作る手間が大きい。Go になったので採らない。No-Go になった場合も、`arin-core` と `arin-platform`(PTY、起動、流量制御)は画面に依存しないので使い回せる。

## 影響

- M2 以降は、xterm.js と DOM 描画を前提に進める。
- 検証用の環境変数 3 つがリリースビルドに残る。値は列挙に直すだけで、不正な値は既定に戻る(`arin-core/src/launch_options.rs`)。外すのは M4(T49)。
- CSP でスタイルの inline を許したままになる。HTML の差し込み(`innerHTML` など)は境界検査で禁止しているので、差し込みの入口は増えていない。
- M1 で見送った項目(寸法の上限、終了済みセッションの解放、終了時の後片付けの時間、`onBinary`、「すべてを選択」、再接続時の寸法、隠したまま作るインスタンスの寸法)は M2 で扱う(`output/tasks/PROGRESS.md`)。
