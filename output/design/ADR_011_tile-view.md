# ADR-011: タイル表示の状態は Rust が持ち、画面は M2 のターミナルの置き場所の仕組みで複数枚を出す

- ステータス: Proposed(本人の了承は M4 の完了確認 T50a。状態は T50b で直す)
- 日付: 2026-11-15
- 決定者: AI(M4 の再分解。T46 の着手時)。PRD・設計書に無い点は【仮定】と書いた
- 関連: PRD FR-048・FR-051〜055・FR-060・FR-061・NFR-009、C-10・C-11・C-23。`ARCH_multi-terminal.md` §1.3 #4、§3.4、§5.1(`DisplayMode`・`TileLayout`)、§6.1・§6.2(`ui.displayMode`)、§7.1「アテンション」、§8、§15.2 #4・#6・#10。ADR-001(描画方式)、ADR-003(xterm.js の要素は React の外)、ADR-010(半透過)。計画 `PLAN_multi-terminal.md` の M4 の節

## コンテキスト

M4 ではタイル表示(全プロジェクトの全ターミナルを自動グリッドで並べ、1 ページ最大 9 枚でページ送り)、タイルとカードの連動、タイルの拡大、タイルのアテンションを作る。設計書は次を決めている。

- グリッドとページ、タイルとカードの連動は `arin-core`(§3.4)
- 表示モードは `state.json` の `ui.displayMode` に保存する。ページと拡大中は保存しない予定(§6.1・§6.2)
- アテンションの判定は「タイル表示=表示中ページ」(§7.1。M4 の実装中にフォーカス中のタイルだけに改めた。判断の 7)
- 表示中ページの要素だけを画面に出し、ほかは出力の取り込みだけ(§1.3 #4、§7.3)

決まっていないのは、ページと拡大中とフォーカスをどこが持つか、タイルのクリックとカードの選択・ページ送りの関係、拡大の形、画面の DOM の持ち方、M4 のショートカット。

## 判断

### 1. 表示の状態は `Workspace` が持ち、計算した結果を写しに載せる

- `Workspace` が表示モード(`tabs` / `tiles`)・表示中のページ・拡大中か(真偽)を持つ。グリッドとページの規則は `arin-core/layout/tiles.rs` の純粋な関数
- 写し(`AppSnapshot`)に `display` を足す: モード、拡大中、ページ、ページ数、グリッド(列×行)、表示中のページのタイルの ID の並び、アテンションのあるページの番号。画面はこれを映すだけで、グリッドの規則を TypeScript に書かない
- 理由: アテンションの判定(Rust の読み取りスレッドの側)が、フォーカス中のタイルとページを知る必要がある。ウィンドウが隠れていても判定できる(§1.3 #5)。設計書 §3.4 の振り分けに合う

### 2. 保存するのは表示モードだけ

`ui.displayMode`(`"tabs"` / `"tiles"`)。無い・知らない値はタブ表示で始め、状態ファイルを退避しない【仮定】。ページと拡大中は保存しない(再起動するとフォーカス中のタイルのページで開く)。

### 3. フォーカス中のタイル=選択中のプロジェクトの表示中のタブ

- タイルのクリックは `focus_terminal`(新しいコマンド): そのタブのプロジェクトを選び、そのタブを表示中にする(FR-053)。ツリーの監視は写しで張り替わる(`tree_watch.rs` の作りのまま)
- タイル表示では「フォーカス中のタイルは必ず表示中のページにある」を保つ。選択・タブの追加・閉じる・前後のあとに、ページをフォーカス中のタイルのページへ合わせ、ページ数が減ったら丸める
- カードを選ぶと、そのプロジェクトの最初のタイルのページへ移る(FR-053)。表示中のタブがそのページに無ければ、最初のタイルを表示中にする【仮定】
- ページを送ると、新しいページの先頭のタイルにフォーカスが移る(プロジェクトが替わる)【仮定】。端では何もしない(循環しない)【仮定】
- タイル表示(拡大中を含む)で、タブが閉じた(⌘W・シェルの終了・プロジェクトの削除)結果フォーカス中のタイルが無くなり、ほかにタイルが残っているときは、閉じたタイルがあった位置のタイル(並びの同じ番号。末尾だったら 1 つ前)にフォーカスを移す(`focus_terminal` と同じ結果。入力のフォーカスが行き場を失わず、アテンションが全タイルに立たない)。カードで 0 枚のプロジェクトを選んだとき・タブ表示では移さない(2026-11-16、M4 のレビューの S4)
- 理由: タブ表示の「表示中」とタイル表示の「フォーカス」を同じ値で表せるので、新しい状態を足さずに済む。M3 の「パスをターミナルに挿入」の宛先(選択中のプロジェクトの表示中のタブ)が、そのままフォーカス中のタイルになる。キー入力が見えないターミナルへ行くことが無い

### 4. 拡大は「タイル表示のまま、タブ表示の形で 1 枚を出す」

- 拡大中は真偽 1 つ(§6.1 の「タイルからの拡大中か」)。右ペインはタブ表示と同じ形(フォーカス中のタイルのプロジェクトのタブバーとそのターミナル)に、元に戻すボタンのあるタイトル帯を足す
- 拡大はタイトルバーのダブルクリックかショートカット。ダブルクリックは対象のタイルの ID を `toggle_tile_maximize` に渡し、Rust が「そのタイルにフォーカスしてから拡大」を 1 回で行う(M4 のレビューの S3)。戻すのは同じショートカット、元に戻すボタン、タイトル帯のダブルクリック【仮定】。ターミナルの本文のダブルクリックは xterm.js の単語の選択なので使わない
- 拡大中にカードやタブを替えると、拡大したままそのタブを出す。表示モードをタブにすると拡大は解ける【仮定】

### 5. 画面は M2 の置き場所の仕組みをそのまま使い、表示中を「並び」に広げる

- xterm.js の要素は React の外に置き、`TerminalHost` が置き場所を描き、`TerminalManager.attach` が要素を置き場所の間で移す(ADR-003、M2)。タブ表示 ↔ タイル表示 ↔ 拡大は、置き場所が替わるだけで、ターミナルを作り直さない
- `TerminalManager.present(shown, background)` の `shown` を 1 枚から並びにする。表示中のページのタイルだけを表示にし、ほかは `setVisible(false)`(描画の資源を手放す。WebGL ならコンテキストを返す)。出力の取り込みと処理済みの通知は続ける(FR-052、NFR-009)
- 各タイルの寸法は `TerminalHost` の `ResizeObserver` → `fit` → `resize_terminal` のまま(FR-051 の 3 つ目の AC)

### 6. M4 のショートカットは表に 4 行を足し、メニューバーに「表示」を足す【仮定】

| コマンドの ID | 既定のキー | 受け口 | 理由 |
| ------------- | ---------- | ------ | ---- |
| `view.toggle-display-mode` | `Cmd+Shift+G`(⇧⌘G) | メニューの項目 | Safari の「すべてのタブを表示」と同じキー |
| `view.previous-page` | `Cmd+Alt+ArrowLeft`(⌥⌘←) | メニューの項目 | 矢印のキーは ⌥ で文字が変わらない。⌘⇧[・⌘⇧] はタブの前後で使っている |
| `view.next-page` | `Cmd+Alt+ArrowRight`(⌥⌘→) | メニューの項目 | 同上 |
| `view.toggle-maximize` | `Cmd+Shift+Enter`(⇧⌘↩) | メニューの項目 | iTerm2 のペインの拡大と同じキー。⌘↩(パスの挿入)と重ならない |

- 受け口はメニューの項目(OS が WKWebView より先に受ける。§15.3 #7)。`on_menu_event` がタブの操作と同じく `SessionRegistry` を呼ぶ。部品とメニューにキーの文字列を書かない(ボタンのツールチップのキーも、画面が受け取った表から引く)
- 「表示」の見出しは「編集」の右。タブ表示でのページ送りと拡大は何もしない(項目は無効にせず並べる)

### 7. アテンション(FR-055)は走査・判定・写しまでを M4 で作る【仮定】

- `AttentionScanner`(BEL 単独、OSC 9 のうち `9;4` 以外、`777;notify`)を読み取りスレッドで常に動かす。契機があったチャンクのあとに `Workspace::note_attention` を呼び、印が立ったときだけ写しを送る
- いま見ている(§15.2 #10 の A)ターミナルには印を立てない。いま見ているのは、どの表示モードでもフォーカス中のターミナル 1 枚(タブ表示は選択中のプロジェクトの表示中のタブ、タイル表示はフォーカス中のタイル、拡大中は拡大した 1 枚。`Workspace::attended_terminals`)。印はそのターミナルがフォーカス中になったら消す(ページを送って見えるようになっただけでは消さない)。画面が描く並び(`visible_terminals`)とは別に決める
  - 理由(2026-11-15 に「タイル表示=表示中のページの全タイル」から改めた): 表示中のページの全タイルを見ている扱いにすると、同じページのタイルに印が立たず、PRD FR-055 の 1 つ目の受け入れ基準「アテンションのあるタイルのタイトルにバッジが付く」(9 枚並べて、どのタイルが入力待ちかに気づく)を満たせない
- M4 の画面が出すのはタイルのタイトルの印と、ページ表示の前後のボタンの印だけ。カードの印・タブのバッジ・macOS 通知は M6(T57)
- 計画の §リスク #3 には「確定: A(2026-11-14 本人承認)」とあるが、T48 の行は【要確認】のままなので、ここでは【仮定】として扱う

### 8. 検証用の指定は段階的に外す

- 9 枚の検証画面(`ARIN_VERIFY_GRID`)は T49c(画面とスモーク)・T49d(Rust と結合テストの足場)で外す。スモークと計測の 9 枚は、一時の状態フォルダに 9 プロジェクトとタイル表示の `state.json` を置いて作る
- `ARIN_RENDERER`・`ARIN_UNICODE`・`RendererLabel` は、T49b で複数枚を実測して ADR-001 に案を書き、本人が T50a で体感を比べてから T50b で外す【仮定】

## 検討した代替案

| 案 | 採らなかった理由 |
| -- | ---------------- |
| ページと拡大中を画面(`uiStore`)に持つ | アテンションの判定(Rust)がフォーカス中のタイルとページを知れない。画面から毎回伝えると、伝える前の出力の扱いがずれる |
| グリッドの計算を画面に置く(写しには並びだけ) | 規則が 2 か所になる(Rust の判定と画面の表示)。§3.4 の振り分けと違う |
| フォーカス中のタイルを、表示中のタブと別の値で持つ | タブ表示に戻したときにどちらを出すかの規則が増える。パスの挿入の宛先の決まりも足す必要がある |
| ページを送ってもフォーカスを動かさない | キー入力が見えないページのターミナルへ届く |
| アテンションの判定で、タイル表示の表示中のページの全タイルを「見ている」とする(当初の設計書 §7.1) | 同じページのタイルのタイトルに印が出ず、FR-055 の 1 つ目の受け入れ基準を満たせない |
| 拡大を表示モードの 3 つ目の値にする | 保存の値が増える。再起動で拡大したまま開くのは PRD の「同じ操作でタイル表示に戻る」に合わない |
| タイルごとに別の xterm.js のインスタンスを作る(タブ用とタイル用) | スクロールバックと PTY の接続が二重になる。§1.3 #4(1 ターミナル=1 インスタンス)と違う |
| ターミナルの本文のダブルクリックで拡大する | xterm.js の単語の選択とぶつかる |
| ページ送りに ⌘⇧[・⌘⇧] を使う | タブの前後(FR-044)とぶつかる |

## 影響

- 写しの `display` と `terminals[].attention` が増える(版は上げない。項目の追加)。`state.json` に `ui.displayMode` が増える(版は上げない)
- ショートカットの表は 22 行になる。M4.5(T63〜)の設定ファイルで、この 4 行もキーを変えられる
- 画面は `TerminalManager.present` の形が変わる。検証画面の撤去で `src-tauri/tests/` の足場が替わる
- 見直す条件: 本人が T50a でページ送り・拡大・キーの振る舞いを変えたいとき。写しの順の入れ替わりで表示が戻る症状が出たとき(写しに通し番号を足す)
