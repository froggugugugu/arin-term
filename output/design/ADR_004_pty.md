# ADR-004: PTY に `portable-pty` 0.9.0 を使い、出力は Tauri のチャネルで生バイトのまま流量制御つきで流す

- ステータス: Accepted
- 日付: 2026-11-14
- 決定者: 本人(設計ゲート)。§15.1 #3 は、推奨どおりで進める旨を提示し、異論がなかったため推奨を採った
- 関連: `ARCH_multi-terminal.md` §1.3 #2・#3・#12・#15、§1.4 #10・#11、§2.1、§2.2、§5.1、§5.2、§7.1、§12、§15.1 #3、§16

## コンテキスト

Arin はターミナル 1 枚につき PTY 1 組を持ち、ログインシェルを起動する(FR-039・040)。1 枚の異常が他へ波及してはならず(NFR-006)、大量出力でも操作が反応し(NFR-004)、タイル 9 枚を同時に表示できる必要がある(NFR-009)。外部通信をしないため、ローカルのソケットも開かない方針である(NFR-008)。

PTY は Rust 側で持つ(§1.3 #2)。そのうえで決めることは 2 つある。

1. PTY をどのクレートで扱うか。
2. PTY の出力を画面(WKWebView の中の xterm.js)へどう流すか。

設計時に確認した事実:

- `portable-pty` 0.9.0 はこの Mac でビルドでき、次が動いた: ログインシェルの起動(`argv[0]` が `-zsh`、ログインかつ対話)、最小の環境変数から始めて PATH が 16 件に組み立てられ `claude` が見つかる、前面プロセスグループがシェルと実行中のコマンドで変わる、行・桁数の変更が端末に届く(§1.4 #11。スクラッチパッドの最小プログラムを `cargo run`)。
- Tauri のチャネルは生バイトを送れる。1024 バイト未満は直接、それ以上は取りに来させる方式で渡す(§1.4 #10。tauri 2.12.5 `src/ipc/channel.rs` を読んで確認)。

## 判断

PTY は `portable-pty` 0.9.0 で扱い、出力は Tauri のチャネルで生バイトのまま画面へ送り、画面が処理し終えた量を返すまで読み取りを止める流量制御をかける。

### PTY のクレート

- `portable-pty` を 0.9.0 の正確な版で指定する(§12「依存の管理」)。
- 使うのは `arin-platform/src/pty/` の `NativePty` だけ。`arin-core` は `PtyPort` を定義し、クレートを知らない(§3.2)。
- 起動するシェル、`argv[0]`、cwd、環境変数の許可リストは Rust 側で決める(§7.1。`ShellLaunchSpec`)。画面からは指定できない(§12)。
- 実行中の判定は、PTY の前面プロセスグループを 1 秒間隔で調べる(§1.3 #15)。

### 出力の流し方

ターミナルごとに読み取りスレッドを 1 本持ち、次の順に処理する(§7.1)。

1. 読み取りスレッドが PTY から読む。
2. `AttentionScanner` が生バイトを走査する(BEL、OSC 9/777)。
3. 短い時間ぶん(数ミリ秒、または一定のバイト数)をまとめ、ターミナルごとのチャネルで画面へ送る。
4. 画面は xterm.js に書き込み、取り込みが済んだ量を Rust に返す(`TerminalSurface.write` の戻り値。§5.1)。
5. 未処理の量が上限を超えたら、Rust は PTY の読み取りを止める。子プロセスは書き込みで待たされる。下限まで減ったら再開する。

- PTY の出力にはイベントを使わない。状態の写しとツリーの変更だけをイベントで送る(§5.2)。
- PTY は画面が最初に接続したときに起動する。接続前の出力を取りこぼさないためである(§1.3 #2)。
- まとめる時間・バイト数と、流量制御の上限・下限の値は未定。M1 で、大量出力のあいだもメモリが増え続けないことを確かめて決める(§2.2「流量制御」)。
- 管理は `src-tauri/sessions`(`SessionRegistry`、`OutputPump`)。

## 代替案

### A: `pty-process` 0.5.4

- メリット: 依存が少ない(`rustix` のみ)。最終リリースが 2026-10 で更新が続いている。
- デメリット: 実績が相対的に少ない(ダウンロード約 590 万。`portable-pty` は約 2,870 万)。`arg0` を自分で指定し、前面プロセスの取得は fd から自分で `tcgetpgrp` を呼ぶ必要がある。この Mac では未検証。
- 採らなかった理由: `portable-pty` は必要な動作をこの Mac で確認済みで、前面プロセスの取得(`process_group_leader()`)とログインシェルの起動の機能を持つため。

### B: 自前実装(`libc` の `openpty` と `fork`)

- メリット: 依存が `libc` だけになる。挙動をすべて自分で決められる。
- デメリット: `fork` と制御端末の扱いを誤ると不具合になる。`unsafe` が増える。ログインシェルの起動と前面プロセスの取得も自分で書く。未検証。
- 採らなかった理由: 誤りやすい部分を自分で抱える利点が、依存を減らす利点を上回らないため。

### C: `tauri-plugin-pty` 0.3.1

- メリット: Tauri のプラグインとしてそのまま使える。
- デメリット: `portable-pty` の薄い包みで、起動するプログラムと引数を画面側が指定する作り。
- 採らなかった理由: 起動の仕様を Rust 側で決める方針(§12)に合わないため。比較の表に入れる前に候補から外した(§2.1)。

### D: 出力をイベントやローカルのソケットで流す

- メリット(イベント): 状態の写しと同じ仕組みで済む。メリット(ソケット): Tauri の IPC を通らない。
- デメリット: ソケットはローカルとはいえ通信の口を開く。イベントで生バイトを送ったときの性能は、設計書では比べていない(未検証)。
- 採らなかった理由: チャネルが生バイトを送れることを確認済みで(§1.4 #10)、ソケットを開かずに済むため(NFR-008)。

## 影響

### ポジティブ

- ログインシェルの起動、PATH の組み立て、前面プロセスの取得、寸法の変更が、この Mac で動くことを確認済みのクレートで始められる。
- PTY は `PtyPort` 越しなので、クレートを替えても影響は `arin-platform/src/pty/` に閉じる(§2.1、§16)。
- ターミナルごとに PTY とスレッドを分けるので、1 枚の異常が他へ波及しにくい(NFR-006)。
- 流量制御で、画面が追いつかないときは子プロセスを待たせ、メモリの増加を抑える設計になっている(NFR-004)。
- 通信の口を開かない(NFR-008)。

### ネガティブ

- `portable-pty` の最終リリースは 2025-02(約 21 か月前)で、更新が止まり気味である。
- 依存が多め(`nix`、`serial2`、`filedescriptor` など)。`/legal-check` と `cargo audit` の対象が増える。
- 流量制御のしきい値とまとめの単位は未定で、M1 の結果しだいで設計を見直す可能性がある。
- チャネルの仕組み上、1024 バイト以上は画面が取りに来る方式になる。大量出力のときの往復の負荷は未計測。
- 画面を再読み込みすると、それまでの出力(スクロールバック)は消える。Rust 側に直近の出力を保持して流し直す案は、今後の拡張に回した(§16)。
