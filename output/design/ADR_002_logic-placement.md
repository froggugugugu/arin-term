# ADR-002: 状態と規則の正本を Rust の `arin-core` に置き、依存方向をビルドと検査スクリプトで強制する

- ステータス: Accepted
- 日付: 2026-11-14
- 決定者: 本人(設計ゲート)。#1 は本人が個別に回答した。#10 は推奨どおりで進める旨を提示し、異論がなかったため推奨を採った
- 関連: `ARCH_multi-terminal.md` §1.1、§1.3 #1・#6、§1.4 #4・#17、§3、§13.1、§15.1 #1・#10、ADR-003

## コンテキスト

Arin は Tauri(Rust + TypeScript)で作る(PRD §7 C3)。PRD は画面のコードを薄くすること(PRD §7 C5)と、依存方向をビルドで守ること(`project-config.md` §2「依存方向チェック」、PRD §7)を求めている。

ロジック層(状態と規則)を Rust と TypeScript のどちらに置くかで、設計の全体(§3〜§7)が変わる。設計書は次の性質を重く見た。

- Arin はファイルを書き換える(新規作成・移動・コピー・ゴミ箱)。その安全の判定を画面から迂回できると、画面に入り込んだスクリプトがユーザーのファイルを壊せる(§12)。
- アテンションの検出、実行中の判定、保存の予約は、ウィンドウが隠れていても動く必要がある。WKWebView は隠れたビューのタイマーを抑え、約 5 分で処理を止めることがある(§1.4 #9。ソースで確認、実機では未実行)。
- tadcap は lint の設定ファイルを持たず、`tsc` の厳格オプションと `cargo clippy -- -D warnings` で検査している(§1.4 #4)。
- TypeScript のプロジェクト参照を使うと、ロジック層から画面層を import した時点と、ロジック層で DOM を使った時点でコンパイルエラーになる(§1.4 #17。TypeScript 6.0.3 の最小構成で `tsc -b` を実行し TS6307・TS2584 を確認)。

## 判断

状態と規則の正本を Rust の `arin-core` に置き、依存方向は Cargo のクレート依存、TypeScript のプロジェクト参照、境界検査スクリプトの 3 つで強制し、コード品質は `tsc` の厳格オプションと clippy で見る。

### ロジックの置き場所(§15.1 #1)

| 置き場所 | 置くもの |
| -------- | -------- |
| Rust(`arin-core`) | ファイルを書き換える処理の手順と安全の判定、バイト列やテキストの解釈・生成(アテンションの走査、シェルエスケープ、状態と設定の読み書きと検証)、ウィンドウが隠れていても動く必要があるもの、保存する状態と PRD が規則として定めているもの |
| TypeScript(`src/logic`) | 画面にどう並べ、どう操作を受けるかの計算だけ(ツリーの行の並び、差分の適用、更新の保留、目印、選択、ドラッグ、キーの振り分け、メニュー項目の組み立て) |

- 画面は Rust から届いた状態の写しを映し、操作を Rust のコマンドに伝えるだけにする。画面が正本を書き換えることはない(§5.2)。
- OS への入出力は `arin-core` のポート(trait)越しに呼び、実装は `arin-platform` に置く。`src-tauri` のコマンドには規則を書かない(§3.2)。
- 振り分けの基準の全体は §3.4。

### 依存方向の強制(§15.1 #1・#10)

| 対象 | 方法 | 判定 |
| ---- | ---- | ---- |
| Rust のクレート間の依存 | `Cargo.toml` の依存宣言(`arin-core` ← `arin-platform` ← `src-tauri`) | `npm run build` が失敗する |
| `arin-core` の依存の中身 | `cargo tree -p arin-core` に禁止クレートが無いことを `scripts/check-boundaries.mjs` で検査する | `npm run lint` |
| `arin-core` の入出力の禁止 | `crates/arin-core/src` に `std::fs` `std::process` `std::net` が無いことを同じスクリプトで検査する。`unsafe` は `#![forbid(unsafe_code)]` | `npm run lint` / コンパイル |
| `src/logic` の独立 | TypeScript のプロジェクト参照。`src/logic/tsconfig.json` は DOM の型と JSX を読み込まず、他のプロジェクトを参照しない | `tsc -b` がエラーになる |
| `@xterm/*` と `@tauri-apps/api` の隔離、`src/ui` からの直接 import | import 文を調べる検査スクリプト | `npm run lint` |
| 外部通信の不在、画面への文字列の差し込み | 同じ検査スクリプト(§3.3) | `npm run lint` |
| `arin-core` 内の機能モジュールどうしの直接参照 | ビルドでは強制できない | コードレビュー |

コード品質の道具は、`tsc` の厳格オプション、`cargo clippy --workspace --all-targets --locked -- -D warnings`、`cargo fmt --check`、境界検査スクリプトとする(§13.1 の `npm run lint`)。ESLint・Biome などの lint は入れない。検査スクリプトの単体テストは `node --test` で書く(tadcap の `scripts/*.test.mjs` と同じ)。

## 代替案

### A: ロジックの正本を TypeScript に置く(§15.1 #1 の B)

状態と規則を画面側(`src/logic` とストア)に置き、Rust は OS への入出力だけを担う。

- メリット: ブラウザ方式の E2E が本物の規則を通る。規則を Vitest で速く回せる。Rust の記述量が減る。
- デメリット: ファイル操作の安全判定を、迂回させないために Rust 側にも二重に書く必要がある。ウィンドウが隠れたときの動作が `backgroundThrottling` の設定(§1.3 #6)頼みになる。依存方向をクレート境界で強制できない。
- 採らなかった理由: ファイルを失わないこと(§1.1 #5)を構造で保証することと、隠れていても動くことを優先した。

### B: 画面側の依存方向とコード品質を lint で検査する(§15.1 #10 の B。Biome など)

- メリット: import の制限やコードの癖を、設定ファイルの規則として宣言的に書ける。React のフックの誤用を検出できる。
- デメリット: 開発用の依存と設定ファイルが増える(PRD §7 C6「依存は最小限」)。tadcap の構成から外れる。プロジェクト参照と検査スクリプトで足りる部分と役割が重なる。
- 採らなかった理由: 依存方向の強制は、プロジェクト参照と検査スクリプトで足りるため。フックの誤用だけは別の問題として残し、M2 の着手時に再検討する(ネガティブの節)。

## 影響

### ポジティブ

- ファイルを書き換える判定を画面から迂回できない。画面に入り込んだスクリプトの被害を、Rust 側の範囲検査で抑えられる(§12)。
- アテンションや実行中の判定が、ウィンドウが隠れていても Rust 側で動く。
- 依存方向の違反の多くがコンパイルエラーか `npm run lint` の失敗になり、レビューに頼らずに済む。
- OS への入出力がポート越しなので、`arin-core` は偽の実装で単体テストでき、PTY などの差し替えは `arin-platform` に閉じる。
- 追加する開発用の依存が無い(tadcap と同じ構成)。

### ネガティブ

- Rust の記述量が増える。
- ブラウザ方式の E2E は偽の Rust 側を通るため、本物の規則を通らない。偽物と実物のずれは型の生成(ADR-006)と Rust 側の結合テストで補う。
- 画面の操作は毎回コマンドを経由するので、写しの往復が要る。
- `arin-core` 内の機能モジュールどうしの直接参照は、ビルドで強制できずレビュー頼みになる。
- React のフックの誤用は `tsc` の厳格オプションでは検出できない。M2 の着手時(T28)に lint の追加を再検討する(ADR-003 と同じ)。
- 境界検査スクリプトは自前で保守する。禁止リストの更新(例: React の `dangerouslySetInnerHTML`)を忘れると検査が漏れる。
