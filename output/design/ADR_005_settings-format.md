# ADR-005: 設定ファイルの形式に TOML を使う

- ステータス: Accepted
- 日付: 2026-11-14
- 決定者: 本人(設計ゲート)。§15.1 #4 は本人が個別に回答した
- 関連: `ARCH_multi-terminal.md` §1.3 #10、§2、§5.1、§6.1、§6.2、§7.2、§15.1 #4・#11、PRD FR-057

## コンテキスト

PRD は、設定を人間が読める 1 ファイルに置き、形式は JSON か TOML から設計で決めるとしている(FR-057)。GUI の設定画面は最小限にする(N5)。

設計書では、設定ファイルについて次を決めている。

- 置き場所は `~/Library/Application Support/Arin/`(C-01b)。状態ファイル `state.json` とは別のファイルにする(§6.2)。
- 書くのは人間だけで、アプリは読むだけ。保存を検知して読み直す。人が書いたコメントや並びを壊さないためである(§1.3 #10)。
- 未知のキーは無視する。範囲外の値は既定値に戻し、理由を画面に出す。構文エラーのときは直前の値を保ち、エラーを表示する(§7.2)。
- キーは `terminal.font_size` のように分類と名前の 2 段で、スクロールバックの行数と目印の時間も設定項目にする(§6.2、§15.1 #11)。

候補は TOML、厳密な JSON、コメント付き JSON の 3 つだった(§2)。設計書には 3 つを比べた表は無く、下の代替案のメリットとデメリットは本 ADR を書くときに整理した。

## 判断

設定ファイルは TOML で書き、ファイル名は `settings.toml` とする。

- 正本は `settings.toml` そのもの。`SettingsStore` は読んだ結果と読み込みエラーを持つだけで、永続化しない(§6.1)。
- ファイルの読み書きは `SettingsFilePort`(実装は `arin-platform` の `FsSettingsFile`。設計時の名前は `SettingsFileStore` で、M4.5 で実装したときにこの名前にした)、スキーマ・既定値・検証は `arin-core/settings`(`Settings`、`SettingsValidator`)に置く(§5.1)。
- 設定のキーは §6.2 の表(提案)。キーの追加は `Settings` にキーと既定値を足すだけで、未知のキーは無視するので旧版と共存できる(§16)。

未定の点:

- TOML を読むクレートとその版は、設計書で決めていない。`arin-core` に許す依存は `serde`、`serde_json`、`thiserror`、`ts-rs` だけ(§3.1)なので、TOML の解析をどのクレートに置くか(`arin-core` に依存を足すか、`arin-platform` で解析して `arin-core` には値を渡すか)は、設定を実装するとき(FR-057 は M6)に決める。
  - **決めた(2026-11-16、ADR-012 の 4)**: 解析は `arin-platform`(`storage/settings_file.rs`)に置き、`arin-core` には節ごとの文字列の対とファイル全体の結果だけを渡す(`arin-core` の依存は増やさない)。クレートは `toml` 1.2.1(`default-features = false`、`std`・`parse`。Tauri が引き込んでいる版と同じ)。公開から 2 週間未満の例外は本人が認めた(ADR-012 の末尾)。M4.5 で読むのは `[shortcuts]` だけ

## 代替案

### A: 厳密な JSON

- メリット: `state.json` と同じ形式で、`serde_json` は既に `arin-core` の依存にある。新しい依存が増えない。
- デメリット: コメントを書けない。人が手で書くと、末尾のカンマや引用符の付け忘れで構文エラーになりやすい。
- 採らなかった理由: 人が書いて読む設定ファイルで、コメントを残せないことを避けたため(§1.3 #10)。

### B: コメント付き JSON

- メリット: コメントを書ける。JSON に慣れた人には読み書きしやすい。
- デメリット: 厳密な JSON の読み込み部品ではそのまま読めず、対応する部品が要る。末尾のカンマなどの書き間違いは厳密な JSON と同じく起こる。
- 採らなかった理由: 設計ゲートで本人が TOML を選んだ(設計書に TOML を選んだ個別の理由は記録されていない)。比べると、コメントを書ける点も新しい依存が要る点も TOML と同じで、JSON 系を選ぶ利点が薄い(この比較は本 ADR を書くときに整理したもの)。

## 影響

### ポジティブ

- 人がコメントを書き込める。アプリは書き換えないので、コメントと並びがそのまま残る。
- `[terminal]`・`[tree]` のような表で、§6.2 の 2 段のキーを素直に書ける。
- 状態(`state.json`。アプリだけが書く)と設定(`settings.toml`。人だけが書く)が、拡張子でも区別できる。

### ネガティブ

- TOML を読むための依存が 1 つ増える(§15.1 #4 の「依存の数」)。`/legal-check` と `cargo audit` の対象が増える(クレートは ADR-012 で `toml` 1.2.1 に決めた。Tauri 経由で既に依存の木にあり、新しいクレートは 0)。
- 状態と設定で形式が 2 つになり、読み込みの部品も 2 つになる。
- 構文エラーの位置を人に分かる形で画面に出す方法は、ADR-012 の 3 で決めた(クレートが返す位置から行と列を数えて 1 行で知らせ、クレートの文言は出さない)。
