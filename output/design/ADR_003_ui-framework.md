# ADR-003: 画面のフレームワークに React と zustand を使う

- ステータス: Accepted
- 日付: 2026-11-14
- 決定者: 本人(設計ゲート)
- 関連: `ARCH_multi-terminal.md` §2、§6.1、§9.1、§10.2、§15.1 #2

## コンテキスト

Arin は Tauri(Rust + TypeScript)で作る(PRD §7 C3)。画面は macOS 標準の WebView の上で動き、カード一覧、ファイルツリー、ターミナルのタブとタイル、確認ダイアログ、コンテキストメニューを持つ。

状態の正本は Rust の `arin-core` にあり、画面はその写しを映す(ADR-002 の主題)。そのため画面側に要るのは、写しが変わったときに表示を正しく更新する仕組みである。

設計書の当初の推奨は「フレームワークなし」(素の TypeScript と DOM。過去作 tadcap と同じ)だった。依存が最も少なく、メモリも最も小さいためである。ただし推奨は僅差で、設計書は「画面の作り込みが今後増える見込みなら React が有利」としていた。

2026-11-14 の設計ゲートで、本人から次の 2 点が示された。

- 画面をリッチにしていきたい要望がある。
- 将来、簡易 Markdown エディタ(過去作 mdslide 程度)を入れる可能性がある。

あわせて、軽さ(G4)の数値目標は同日に目安へ格下げされており(PRD §10 C-14)、フレームワークによるメモリの増加は合否に影響しない。

## 判断

画面のフレームワークに React を、画面側のストアに zustand を使う。

- React の部品は `src/ui` に `.tsx` で置く。`src/logic` は DOM も React も使わない(TypeScript のプロジェクト参照で強制する)。
- zustand のストアは Rust の状態の写しと、表示だけの状態を持つ。規則や判定を書かない。ストアは生成関数で作り、`main.tsx` から props で渡す。
- xterm.js の要素は React の管理の外に置く。再描画でターミナルが作り直されないようにするためである。

### 部品のテスト

React の部品(`src/ui`)の単体テストは書かない。

- 部品の振る舞いは Playwright(ブラウザ方式)で見る。
- 判定は部品に書かず、`src/logic` と zustand のストアに寄せ、Vitest で見る。ストアは React なしで動かせる。
- テスト用の DOM とライブラリ(jsdom、Testing Library)を足さない(PRD §7 C6「依存は最小限」)。

部品に判定が溜まり、Playwright だけでは遅い・不安定になった場合は、この方針を見直す。

## 代替案

### A: フレームワークなし(素の TypeScript と DOM)

設計書の当初の推奨。tadcap と同じ。

- メリット: 依存が増えない。メモリが最も小さい。tadcap の構成をそのまま踏襲できる。
- デメリット: ツリーの仮想スクロールと行の更新、カードやタブの表示の同期を自前で書く。画面が増えるほど、表示の同期ずれが起きやすくなる。
- 採らなかった理由: 画面をリッチにしていく要望があり、自前で書く量が増え続けるため。

### B: SolidJS または Svelte

- メリット: React より軽い。宣言的に書ける。
- デメリット: 本人に経験がない。エージェントが書いたコードを本人がレビューしにくい。
- 採らなかった理由: 本人が読めることを優先した。React は mdslide で経験がある。

## 影響

### ポジティブ

- 表示を宣言的に書けるので、状態の写しと表示の同期ずれが起きにくい。
- 本人が mdslide で使っており、コードを読める。
- 画面を作り込む余地が広がる。

### ネガティブ

- 依存が増える(実行時 3、開発時 3)。
- メモリは「フレームワークなし」より増える見込み。どの程度かは計測していない。NFR-001 の数値は目安で、合否判定に使わない。
- React のフックの誤用は `tsc` の厳格オプションでは検出できない。M2 の着手時(T28)に lint の追加を再検討する。
- 境界検査の禁止リストに `dangerouslySetInnerHTML` を足す必要がある(設計書 §3.3 に反映済み)。
- xterm.js の要素を React の管理の外に置く決まりを守らないと、再描画でターミナルが作り直される。

### 簡易 Markdown エディタについて

エディタは、この判断の理由の一つではあるが、**いまの設計と計画には含まれない**。要求メモの非ゴール N1(テキストエディタ)と N7(ファイルの中身に触れる機能)に当たるためである。入れるには、要求メモの非ゴールの変更(人間ゲート)と PRD の改版が要る。
