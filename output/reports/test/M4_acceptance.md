## 計測(9 枚のタイル表示。Apple M5、参考値。合否にしない)

| 項目 | DOM 描画 | WebGL 描画 |
| ---- | -------: | ---------: |
| 起動 → シェルが 9 個そろう | 約 320ms | 約 320〜430ms |
| 本体 + WebKit のメモリ(起動直後) | 約 100 MiB | 約 120 MiB |
| 9 枚に 4 MiB ずつ流し終えるまで(実アプリ) | 約 1.0 秒 | 約 1.0 秒 |
| 9 枚が取り込み終えるまで(画面だけ。2 MiB ずつ) | 約 370ms | 約 330ms |
| ページを送って描き終わるまで | 約 40ms | 約 80ms |

- Rust 側: 9 枚に同時に流したときの全体の速さは 1 枚のときと同じ(約 100 MiB/s)。流量制御は 9 枚それぞれで効く。アテンションの走査を常に行っても、読み取りは遅くなっていない。
- 全体は `testreport/perf/latest.md`。描画方式と全角幅の方式の案は `output/design/ADR_001_terminal-engine.md` の「M4 の実測と案」(DOM 描画と `unicode11` を既定のままにする案。決定は本人)。

## 完了前のレビューで見つけて直したもの

- タイル表示で、表示中のページのタイルにアテンションの印が一切付かない(「見えているターミナルには立てない」という規則だった。フォーカス中のターミナル以外に立てる規則に改めた。ADR-011)
- ツリーから別のタイルへ落とすと、入力だけがそのタイルに移り、フォーカス中の輪やカードが元のまま
- 写しを作って送るまでが直列でなく、古い写しがあとから届いて画面が古い状態に戻りうる(M2 から残っていた問題。送り手が増えた)
- クリック以外(Tab キーなど)で別のタイルに入力のフォーカスが入ると、Rust のフォーカスと食い違う
- タイトルバーのダブルクリックで、別のタイルが拡大されうる
- タイル表示でフォーカス中のタイルが閉じ、そのプロジェクトのタブが 0 枚になると、ほかにタイルがあってもフォーカスが無くなる
- 登録済みのフォルダの再登録で、カードの選択と移る先が違う
- シェルの終了と同時にそのタイルをクリックすると、診断に失敗が 1 行出る
- M3 から残っていた: プロジェクトを切り替えたあとに届いた前のプロジェクトの応答で、衝突の確認が開きうる

## 判断が要る点・残っている問題

| 項目 | 状態 |
| ---- | ---- |

| M4 の 4 つのキー | ⇧⌘G(切替)・⌥⌘←・⌥⌘→(ページ)・⇧⌘↩(拡大)は仮置き。M4.5 の設定で変えられるようにする。実機で効くか・JIS 配列は未確認 |

## 誰も確かめていないこと(本人の確認の範囲)

- 9 枚を並べたときの体感(入力の遅れ、スクロール、ページ送り、タイルのクリック)。Claude Code を何枚か動かした状態で
- DOM 描画と WebGL 描画の見え方と重さの違い(比べ方は進捗ノート)
- 実際のキー(⇧⌘G、⌥⌘←、⌥⌘→、⇧⌘↩)が効くか。US と JIS の配列
- すりガラスの上での、タイトルバー・区切り線・切替のボタン・アテンションの印の見え方(ライトとダーク)
- Claude Code が入力待ちになったとき、フォーカス中でないタイルと、別のページのページ送りのボタンに印が出るか
- ツリーからタイルへのドラッグの手触りと、落としたあとにカードとツリーが落とした先のプロジェクトに替わる動きが使いやすいか
- タイトルバーのダブルクリックでの拡大の手触り
- 長く流しっぱなしにしたとき、メモリが増え続けないか(計測は 1 枚 4 MiB まで)
